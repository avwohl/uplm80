2026-09-22 - two loose ends from the string-literal fix, neither owned by this
repo.

The debt this file recorded against 0.3.4 is discharged: tests/test_parser.py
now has TestStringLiterals, covering a backslash in a character literal, a
doubled quote inside a string, and a string that crosses a line break, plus a
code-generation case so the backslash has to survive as far as the emitted
5CH.  uplm80/_plm_parser.py is generated, so a regen against a grammar that
reintroduced C escape semantics would otherwise still have gone unnoticed.

What is still owed, elsewhere:

  * ../uplox examples/plm_subset.uplox still declares /'([^'\n]|'')*'/, which
    is wrong in the other direction.  Real PL/M source does carry a string
    across a line break - the LITERALLY bodies in the MP/M 2 corpus do, and
    UTIL2/MSBRS.PLM holds a six-line one.  Only its own tests consume that
    grammar, so it was left alone.  plm_full.uplox and plm_pre.uplox were
    fixed in uplox 3.3.1 and are what this repo vendors.

  * ../80un src/plm/bas.plm still writes MBASIC's integer-divide token as 5CH
    rather than '\', the workaround from when the lexer refused the literal.
    Reverting it is safe now, but 5CH also builds against an older uplox, so
    it is a judgement call rather than a defect.

Also note, for whoever rebuilds the committed binaries:

  * scripts/regen_parser.sh cannot run here - ../uplox is not checked out.
    The vendored uplm80/_plm_parser.py matches uplox 3.3.1, which is the
    declared floor.

  * The 0.3.5 code-generation fixes change the emitted code for ../80un.  Its
    output is byte-identical on all 21 corpus samples, but the committed
    80un.com and 80unbas.com need a rebuild to stay reproducible.
